ADR-0004: Use SQLAlchemy 2.0 + Alembic for ORM and migrations

Status: Accepted

Context:
Blueprint Part 4.3 proposes SQLAlchemy and Alembic. The foundation needs an ORM for database models and a migration tool for schema evolution.

Problem:
Choose the Python ORM and migration tool.

Options:
1. SQLAlchemy 2.0 + Alembic — mature, typed (2.0 style), autogenerate migrations, wide adoption.
2. SQLModel — built on SQLAlchemy + Pydantic, less mature migration story.
3. Django ORM — coupled to Django, not suitable for standalone FastAPI app.
4. Tortoise ORM — async-first but smaller ecosystem, less migration tooling.

Decision:
Use SQLAlchemy 2.0 with DeclarativeBase and Alembic for migrations.

Consequences:
- `packages/core/database.py` provides `Base`, `get_engine()`, `get_session_local()`, `get_db()`.
- `packages/core/models.py` defines `Publication` with 2.0-style `Mapped[]` annotations.
- Alembic `env.py` imports `Base` and `models` so `target_metadata` is populated for autogenerate.
- Migration `8054612ce976` created `publications` table.

Security implications:
- Parameterized queries via SQLAlchemy ORM reduce SQL injection risk.
- Connection args for SQLite (`check_same_thread=False`) are dev-only.

Alternatives rejected:
- SQLModel: appealing but Alembic integration less proven; SQLAlchemy alone is sufficient.
- Tortoise: smaller migration and plugin ecosystem.

Date: 2026-11-14
