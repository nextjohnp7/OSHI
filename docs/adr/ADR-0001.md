ADR-0001: Use SQLite for local development, PostgreSQL for production

Status: Accepted

Context:
OSHI needs a relational database as the primary source of truth (Blueprint Part 4.3). PostgreSQL is the production target (with pgvector and PostGIS extensions), but requiring PostgreSQL during initial development and testing creates friction for contributors and slows down the feedback loop.

Problem:
How to configure the database so local development is zero-config while production uses PostgreSQL without code changes.

Options:
1. Hardcode SQLite everywhere — not viable for production (no pgvector/PostGIS, limited concurrency).
2. Hardcode PostgreSQL everywhere — blocks local development without a running PostgreSQL instance.
3. Use `DATABASE_URL` environment variable with SQLite default — SQLAlchemy supports both dialects via connection string.

Decision:
Use `DATABASE_URL` environment variable. Default is `sqlite:///./oshi_dev.db` for local development. Production sets `DATABASE_URL` to a PostgreSQL URL (e.g. `postgresql+psycopg2://user:password@localhost:5432/oshi`). No code change required to switch.

Consequences:
- Local dev and CI run immediately without external services.
- Production gets full PostgreSQL features (pgvector, PostGIS).
- SQLite-specific connection args (`check_same_thread`) handled in `get_engine()`.
- Alembic migrations read `DATABASE_URL` from OSHI settings.

Security implications:
None direct. Production database credentials must be injected via environment, never committed.

Alternatives rejected:
- Docker Compose for local PostgreSQL: adds operational complexity at this stage. Revisit when pgvector is needed locally.

Date: 2026-11-14
